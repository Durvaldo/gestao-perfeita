# SPEC-0001 — Visão do profissional restrita ao próprio trabalho

- **Status**: aprovada (tasks geradas em 2026-10-04; ver o índice em README.md)
- **Criada em**: 2026-10-04
- **Origem**: anotações do responsável (2026-10-04): "Não tem porque os barbeiros verem a parte de outros barbeiros. Produtos e serviços também não. Um barbeiro pode abrir uma comanda pra um outro barbeiro, mas dá erro já que ele não pode ver. Poderia então deixar direto pra ele abrir só pra ele mesmo."
- **Módulo**: `web`

## Contexto

A matriz de permissões de hoje ([ADR-0006](../decisions/0006-autorizacao-policies-funcoes-puras.md), `web/src/lib/authz/policies.ts`) manteve a paridade com o legado:

- `customer`, `service`, `product` e `professional` podem ser lidos por toda a equipe (`catalogPolicy`). Por isso o profissional vê no menu (`web/src/components/shell/nav-items.ts`) e consegue abrir as telas **Barbeiros**, **Serviços** e **Produtos**, só para leitura.
- O profissional pode **criar** comanda e agendamento para qualquer colega, mas só **vê** os próprios (`visibleToActor`). A tela de comanda avulsa (`web/src/app/(app)/comandas/orders-screen.tsx`) oferece todos os barbeiros no select. Quando ele escolhe outro barbeiro, a comanda é criada, mas o redirecionamento para `/comandas/[id]` termina em erro, porque ele não tem permissão para ver essa comanda.

## Objetivo

O profissional entra no painel e vê só o que diz respeito ao próprio trabalho: a própria agenda, as próprias comandas e os clientes. Os cadastros da barbearia continuam sendo assunto do admin.

## Requisitos

### RF-1 — Menu e telas de cadastro só para o admin

Os itens **Barbeiros**, **Serviços** e **Produtos** do menu ficam visíveis só para o admin. Se o profissional acessar `/barbeiros`, `/servicos` ou `/produtos` direto pela URL, recebe a mesma resposta de uma tela sem permissão (redirecionar para o dashboard ou mostrar 404; a implementação escolhe, desde que seja igual nas três).

**Aceite:** logado como `carlos@barbearia-centro.com`, o menu não mostra os três itens, e abrir as três URLs não exibe nenhum dado.

> **Revisão de 2026-10-04 (`TASK-0022`):** a tela `/barbeiros` é também onde o profissional edita os **próprios horários de trabalho**, uma capacidade que já existia ([ADR-0006](../decisions/0006-autorizacao-policies-funcoes-puras.md)) e que esta SPEC não pretendia tirar. Por isso, para o profissional, ela não sumiu: aparece no menu como **"Meus horários"** e lista só o registro dele (RF-2), sem nenhum dado de colega. **Serviços** e **Produtos** saíram do menu e respondem 404, como previsto. A leitura dos horários de trabalho de um colega pela API também passou a ser recusada (403).

### RF-2 — A API de leitura continua servindo aos formulários

O profissional ainda precisa listar serviços (formulário de agendamento) e produtos (adicionar item na comanda). As leituras de `/api/services` e `/api/products` continuam liberadas para ele. A API de profissionais (`/api/professionals`) devolve para o profissional **só o próprio registro**.

**Aceite:** como profissional, `GET /api/services` e `GET /api/products` respondem 200; `GET /api/professionals` lista só ele; `GET /api/professionals/{id de um colega}` responde 404 (ou 403).

### RF-3 — Profissional abre comanda só para si mesmo

Ao abrir uma comanda avulsa, o profissional não escolhe o barbeiro: a comanda é dele. Na UI, o campo "Barbeiro" não aparece (ou aparece fixo, sem edição). No servidor, `POST /api/orders` feito por um profissional usa o profissional dele e **recusa** um `professionalId` de outra pessoa (403 ou 422 com mensagem em pt-BR). O admin continua escolhendo qualquer barbeiro.

**Aceite:** teste de API: profissional abre comanda avulsa sem `professionalId` → 201, com ele como barbeiro; com o `professionalId` de um colega → recusado. Na tela, o fluxo abre a comanda e mostra o detalhe sem erro.

### RF-4 — Matriz de permissões atualizada

`policies.ts` e a matriz de `web/src/lib/authz/__tests__/policies.test.ts` refletem RF-1 a RF-3. Os pontos de "paridade mantida de propósito" da ADR-0006 e da [ADR-0011](../decisions/0011-comandas-estoque-e-duplicidade.md) que esta SPEC muda ("o profissional cria comanda para qualquer colega") devem ser anotados nessas ADRs como superados por esta SPEC.

**Aceite:** `npm test` passa com a matriz nova, e as duas ADRs apontam para esta SPEC.

## Fora de escopo

- Esconder a tela **Clientes** do profissional (ele precisa dela para consultar contatos; a escrita já é só do admin).
- Permissões novas (ex.: profissional que também cadastra produto). Hoje só há os papéis `admin` e `professional`.

## Questões em aberto

- **Q1 — Agendamento para colega.** O agendamento tem o mesmo problema da comanda: o profissional pode criar para um colega e depois não enxerga o que criou (ADR-0006/0009). A anotação fala só de comanda. Alternativas: (A) aplicar a mesma regra do RF-3 ao agendamento; (B) manter, porque o barbeiro às vezes encaixa um cliente na agenda de um colega. Recomendação: **A**, por coerência, se o responsável confirmar que o encaixe para colega não é um uso real.
- **Q2 — Dashboard do profissional.** Hoje o profissional vê o dashboard da barbearia inteira, inclusive o faturamento de cada colega no ranking. Essa decisão estava pendente desde a `TASK-0017`. Alternativas: (A) filtrar todos os widgets pelos dados dele; (B) mostrar a barbearia, mas esconder o ranking de faturamento; (C) manter. Recomendação: **A**, pelo mesmo princípio desta SPEC.

## Decisões do responsável (2026-10-04)

- **Q1 — Agendamento para colega:** **A**. O profissional cria e remarca agendamento só na própria agenda; o admin, em qualquer uma (`TASK-0024`).
- **Q2 — Dashboard do profissional:** **A**. Todos os widgets ficam filtrados pelos dados do próprio profissional; o admin continua vendo a barbearia inteira (`TASK-0025`).
