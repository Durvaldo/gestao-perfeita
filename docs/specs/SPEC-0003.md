# SPEC-0003 — Agenda: sem agendamento retroativo e atendimento concluído contando no dashboard

- **Status**: implementada (2026-10-05; tasks no índice em README.md)
- **Criada em**: 2026-10-04
- **Origem**: anotações do responsável (2026-10-04): "Não deixar agendar retroativo. Somente de hoje para frente." e "Clientes atendidos na agenda não estão entrando para o Dashboard como atendidos."
- **Módulo**: `web`

## Contexto

- **Retroativo.** As regras de agendamento (`web/src/server/appointments/rules.ts` e `appointments.ts`) checam expediente, conflito e profissional inativo ([ADR-0009](../decisions/0009-agendamento-fuso-por-tenant-e-regras.md)), mas não comparam o horário com o momento atual. Dá para criar um agendamento para ontem.
- **Atendidos no dashboard (bug de regra).** O dashboard (`web/src/server/dashboard/dashboard.ts`) conta **só comandas pagas**. O widget "clientes mais frequentes" agrupa `orders` com `status = paid`. Um agendamento marcado como concluído na agenda, sem comanda fechada, não conta como atendimento em nenhum lugar.

## Objetivo

A agenda só aceita horários futuros, e todo cliente atendido aparece no dashboard, tenha ou não passado por uma comanda.

## Requisitos

### RF-1 — Recusar agendamento no passado

Criar um agendamento com início antes do momento atual (no fuso da barbearia) é recusado com 422 em `startsAt`: "Não é possível agendar em um horário que já passou." A regra vale para o admin e para o profissional. Remarcar (mudar o horário de um agendamento existente) para o passado também é recusado.

Atualizar **só o status** de um agendamento passado continua permitido, para poder confirmar, concluir ou cancelar depois do horário. Isso segue a regra da ADR-0009 de que a atualização só de status não revalida o expediente.

**Aceite:** testes de API: criar no passado → 422; remarcar para o passado → 422; marcar como concluído um agendamento de ontem → 200. Na tela, o calendário não abre o formulário ao clicar num horário que já passou, e o campo de data/hora não oferece datas anteriores a hoje.

### RF-2 — Agendamento concluído conta como atendimento

No dashboard, um cliente conta como atendido quando tem um **agendamento concluído** (`completed`) **ou** uma **comanda paga sem agendamento** (avulsa). Um agendamento concluído que também tem comanda paga conta **uma vez só**. O widget de clientes mais frequentes passa a usar essa contagem.

Os widgets de faturamento (ranking de profissionais, mais vendidos) continuam usando só comandas pagas, porque precisam de valor.

**Aceite:** teste do dashboard com (a) um agendamento concluído sem comanda, (b) um agendamento concluído com comanda paga e (c) uma comanda avulsa paga, todos do mesmo cliente → 3 atendimentos. Nenhum caso é contado duas vezes.

## Fora de escopo

- Políticas de antecedência e janela para o cliente final (Bloco B do [plano de melhorias](../PLANO_MELHORIAS_BENCHMARK.md)). Elas são outra regra, valem para a página pública e não para o admin.
- Obrigar uma comanda para concluir o agendamento.

## Questões em aberto

- **Q1 — Tolerância para registro tardio.** Às vezes o barbeiro atende um cliente sem ter agendado e quer registrar o atendimento depois. Com o RF-1, isso não dá mais certo pela agenda. Alternativas: (A) sem tolerância; o atendimento sem agendamento é registrado por comanda avulsa, que já existe; (B) aceitar até X minutos no passado. Recomendação: **A**, já que a comanda avulsa cobre o caso e o RF-2 a conta como atendimento.
- **Q2 — Indicador de "atendidos no período".** A anotação fala em "entrar como atendido". Se o responsável espera também um número de clientes atendidos no período (hoje, mês), isso é um widget novo, que pode entrar nesta SPEC ou numa próxima.
