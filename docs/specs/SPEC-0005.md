# SPEC-0005 — Telefones gravados só com dígitos e exibidos com máscara

- **Status**: aprovada (tasks geradas em 2026-10-04; ver o índice em README.md)
- **Criada em**: 2026-10-04
- **Origem**: anotações do responsável (2026-10-04): "Telefones vão ser sempre colocados e salvos somente com os números; nós colocamos as máscaras para mostrar para o usuário, tanto no input quanto na tabela."
- **Módulo**: `web`

## Contexto

Os campos de telefone (`customers.phone`, `users.phone`, `tenants.phone` em `web/prisma/schema.prisma`) são texto livre. O schema de clientes (`web/src/server/customers/customers.ts`) aceita até 30 caracteres de qualquer tipo, a tela de clientes usa um `<Input>` comum e a tabela mostra o valor como foi digitado. O mesmo número pode estar gravado como `(11) 98765-4321`, `11987654321` ou `11 98765 4321`. Isso atrapalha buscar cliente pelo telefone, gerar links de WhatsApp ([SPEC-0008](SPEC-0008.md)) e, mais tarde, identificar o cliente na página pública.

## Objetivo

Todo telefone fica gravado num formato único, só com dígitos, e o usuário sempre o vê formatado.

## Requisitos

### RF-1 — Gravar só dígitos

A API remove tudo que não for dígito antes de validar e gravar. Telefone válido tem **10 dígitos** (fixo: DDD + 8) ou **11 dígitos** (celular: DDD + 9 + 8). Fora disso, 422 em pt-BR: "O telefone deve ter DDD e 8 ou 9 dígitos." A regra vale para todo campo de telefone que a API recebe (clientes, profissionais/usuários e barbearia). Fica num helper único de normalização e validação no servidor.

**Aceite:** testes: `"(11) 98765-4321"` → gravado `"11987654321"`; `"1133334444"` → aceito; `"98765-4321"` (sem DDD) → 422.

### RF-2 — Máscara no input e na exibição

Os inputs de telefone aplicam a máscara enquanto o usuário digita: `(11) 98765-4321` para 11 dígitos e `(11) 3333-4444` para 10. As tabelas e os detalhes mostram o telefone com a mesma máscara. A formatação fica num helper único em `web/src/lib/format.ts`, ao lado das outras formatações pt-BR.

**Aceite:** teste unitário do helper (10 e 11 dígitos, e valor parcial durante a digitação); na tela de clientes, o número aparece mascarado no formulário e na tabela.

### RF-3 — Normalizar os dados existentes

Uma migration de dados remove os não dígitos dos telefones já gravados. Registros que, depois disso, não tiverem 10 ou 11 dígitos não são apagados nem alterados além da limpeza: eles são listados no log da migration, para revisão manual.

**Aceite:** depois da migration, os telefones do seed e do banco de dev só têm dígitos, e o seed passa a gravar só dígitos.

## Fora de escopo

- Telefones internacionais.
- Unicidade do telefone por barbearia (será necessária para identificar o cliente na página pública, no Bloco C do plano de melhorias).

## Questões em aberto

- **Q1 — Código do país.** O [plano de melhorias](../PLANO_MELHORIAS_BENCHMARK.md) (Passo C2) sugeria E.164 (`+5511...`). A anotação pede "somente os números". Alternativas: (A) gravar só DDD + número (10 ou 11 dígitos) e acrescentar o `55` na hora de montar link ou mensagem de WhatsApp; (B) gravar com `55` (12 ou 13 dígitos). Recomendação: **A**. O produto atende só o Brasil, a máscara fica mais simples, e acrescentar o `55` é trivial. Se for aceita, esta SPEC substitui o trecho de E.164 do Passo C2.
